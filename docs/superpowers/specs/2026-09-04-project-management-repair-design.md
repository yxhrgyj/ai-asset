# 项目管理模块修复设计

## 1. 背景与现状

当前工作区的实际应用位于 `E:/Objects/ai-asset-platform`。用户提供的截图对应 `/projects` 页面：页面主体能渲染，但缺少全局顶部栏和侧边栏。对当前工作区做只读验证得到：

- `frontend` 的 `npm run build` 在类型检查阶段失败；失败点包括 API 泛型返回值、项目详情页模块路径、用户页参数、编辑器类型和样式声明。
- `/projects` 与 `/projects/:id` 路由直接渲染页面，没有使用其他业务页面共用的 `MainLayout`。
- 项目/团队 API 封装声明返回业务对象，但页面仍按 `{ data: ... }` 结构读取，导致运行时数据赋值错误。
- 项目详情页引用不存在的 `../api/assets`，并且使用了与 API 封装不一致的返回结构。
- 导航包含 `/project-rules` 链接，但没有对应路由。
- 后端当前可启动，已有测试可运行，但项目模块缺少足够的接口和边界回归覆盖。

## 2. 目标与非目标

### 目标

1. 前端生产构建通过，不再依赖放宽类型检查来掩盖错误。
2. 项目列表、创建、编辑、归档、详情、规则绑定和合并规则展示使用一致的 API 契约。
3. 项目相关页面与其他业务页面共享 `MainLayout`，在桌面视口恢复完整导航和内容边距，并保持窄视口可用。
4. 修复现有构建错误涉及的相邻页面，避免修完项目页后整体仍不可构建。
5. 为本次回归增加可重复的前端契约测试/静态检查和后端关键接口测试，并执行 HTTP 冒烟验证。
6. 保留工作区已有未提交业务改动，不回退、不覆盖、不清理用户文件。

### 非目标

- 不重写 Vue 或 Spring Boot 架构。
- 不改变资产、审批、统计等模块的业务规则，除非其当前编译错误阻断整体构建。
- 不把项目数据迁移到新的存储方案，也不引入新的第三方 UI 框架。
- 不把截图中的浏览器/系统提示当作产品功能实现。

## 3. 方案与边界

采用最小侵入的契约修复方案：保留现有 `fetch` 客户端和页面组件，令客户端请求函数支持显式泛型；所有 API 方法直接返回业务数据（而不是隐式混用 Axios 风格的 `response.data`）；页面按该单一契约消费数据。

项目页面直接在模板根节点使用 `<MainLayout>`，并在脚本中导入它。项目详情页继续复用现有 `assetApi`，不创建重复的资产客户端。导航中的“项目规则”链接改为已有项目管理入口（或在确认存在实际页面后再保留），避免点击后落入空路由。

后端只做契约和安全边界修复：列表默认排除已归档项目、创建/更新输入做明确校验、规则绑定确认项目和资产版本存在且满足发布状态；不改变既有数据库迁移历史。

## 4. 组件与数据流

### 4.1 前端数据流

`Projects.vue`：

1. 路由守卫确认会话。
2. `projectsApi.list()` 返回 `Project[]`；页面显示加载、空态或错误态。
3. 创建/更新/归档成功后重新加载列表，失败时显示可读错误且保留表单输入。
4. 创建表单提交前在客户端做必填和技术栈去重校验；服务端错误仍作为最终权威。

`ProjectDetail.vue`：

1. 并行/顺序加载项目、合并规则、项目规则和可选规则资产。
2. 任一请求失败时显示页面级错误和返回项目列表的入口，不渲染半成品数据。
3. 规则添加/移除成功后刷新受影响的两个视图；冲突和权限错误使用统一提示。

### 4.2 后端数据流

Controller 从会话取得当前用户 → Repository 查询 → DTO 映射 → JSON 返回。项目访问权限在详情、规则列表、规则变更和合并规则端点保持一致；归档项目不出现在默认列表，也不能继续新增绑定。

## 5. 错误处理与兼容性

- 客户端请求统一处理非 2xx 响应；保留服务端返回的消息，缺失时使用页面级中文兜底提示。
- 204 响应继续映射为 `undefined`，调用方不读取不存在的 `data` 字段。
- `techStacks`、`tags`、`pathGlobs` 等数组字段在 DTO 与前端类型中保证为数组，服务端空值归一化为空数组。
- Markdown 渲染保持现有库；仅补齐 TypeScript 模块声明或改用已有可类型化入口，不关闭 `noImplicitAny`/未使用检查。
- 所有页面在加载期间禁用会重复提交的操作，组件卸载后不更新已失效状态。

## 6. 测试与验收

### 自动化验证

- 新增一个前端 API 契约测试（或等价的类型级测试），证明项目列表、详情和团队列表按直接业务对象消费。
- 新增/补充后端项目接口测试，覆盖：当前用户列表隔离、归档过滤、重复 slug、无权访问、规则绑定冲突及未发布版本拒绝。
- 先运行针对性失败测试确认能捕获现有问题，再实现修复并运行其绿色版本。
- 运行 `npm run build`、`mvn test`，记录退出码和失败数。

### 手工/HTTP 冒烟

使用本地服务和测试账号验证：

1. 登录后打开 `/projects`，能看到完整顶栏/侧栏和空态或项目卡片。
2. 创建项目后列表立即出现项目；刷新后仍存在。
3. 进入详情页可加载合并规则和项目规则；添加、移除、下载操作不报错。
4. 归档后项目从默认列表消失，直接访问受控且不会产生新绑定。
5. 资产、团队、审批等已有页面仍能通过构建并可进入。

## 7. 风险与回滚

- 工作区已有大量未提交改动；所有编辑限定在本设计/计划列出的文件，修改前保留差异，必要时按文件粒度回退本次改动。
- 数据库测试若受本机服务限制，记录限制并至少执行编译、单元测试和已运行实例的 HTTP 冒烟，不修改生产数据。
- 不修改已应用 Flyway 脚本；如确需 schema 变更，另建版本脚本并单独验证，本次设计默认不需要。

## 8. 完成标准

只有在以下条件全部满足后才报告完成：前端构建退出码为 0；后端测试无失败；项目主流程 HTTP 冒烟通过；工作区差异显示没有意外删除或覆盖用户原有改动；剩余已知问题被明确记录。
